## Architecture and implemented behavior

- Approved **Work → Edition → Source** remains intact. No SQL tables/columns were added. Explicit source resolution rejects ambiguous multi-source works. External/blank sessions do not invent canonical work IDs.
- Source-bound jobs and image/certificate asset IDs are owned by one WebContents/main frame. Renderer cannot supply arbitrary worker paths. Binary operations run in utility/Python subprocesses or a strictly loopback-validated Stirling-PDF sidecar (`127.0.0.1` / `localhost`) with deadlines, size limits, progress and process-tree cancellation. Secrets go through stdin or local loopback multipart fields only.
- Mutations chain in private working files. Originals remain unchanged until Save. Safe Save verifies original/output SHA-256, fsyncs a sibling pending file, creates a backup, and atomically replaces; there is no delete-original fallback. New-file publication is exclusive. New Edition/Work saves use existing repositories. Original backups intentionally retain private data; deletion/sanitization of those files is a separate user decision.
- Existing PDF reading remains available. A single `activePanel` controls reader drawers; the workstation is mutually exclusive with the other tools. Safe Save invalidates work-level FTS and emits a reader reload notification.
- Arabic/English labels use centralized translations. Document coordinates remain physical and independent of UI direction. Mobile places tool controls before the preview; desktop uses a wider preview plus controls. Native screenshots exercised 480/1280 widths in both languages.
- Review threads reuse existing `annotations` and JSON anchors, bound to source/hash; comment body remains plain text. Status/reply changes reject stale versions. HTML summary escapes content. PDF embedding writes actual sticky/free-text/ink annotations to a working copy. Display authors are unverified local names, not collaborative account identities.
- AI uses the saved source and existing configured provider; it never fabricates a fallback. Exact page quotes are checked before accepting output. Text transfer to a remote provider requires an explicit checkbox; local Ollama requires an IP loopback endpoint with redirects disabled. Quotes establish provenance, not factual correctness of an inference. Missing AI service/model remains an explicit failure, not a generated mock.

## Verification and limits

The initial eleven-scenario run has been extended in `scripts/verify-pdf-engine.py`: bilingual creation/extraction/preview, replacement, page manipulation/imported thumbnails, image movement/crop, independent text/vector/image redaction checks, AES-256 retention and empty-user permission enforcement, editable/semantic exports, dense bilingual OCR, positive/negative veraPDF results, metadata repair, pending fields, real signing and incremental tampering. `tests/services/pdf-editor.test.ts`, `pdf-stirling.test.ts`, `pdf-cloud.test.ts`, `pdf-collaboration.test.ts` and `tests/ui/reader-panels.test.ts` exercise parser/publication, ownership, Stirling-PDF loopback multipart execution and JAR version discovery, OAuth/network boundaries, review concurrency, citation rejection and audit tampering.

Native `scripts/pdf-workstation-live/run.mjs` isolated profiles exercise real IPC/parser/previews, bilingual widths, OS-encrypted client-ID setup, blank creation, save-as-Work/Edition and Safe Save/backup behavior. No browser login is launched. A controlled PDF/A-2b positive fixture passes; other conformance profiles, complete export visual fidelity, Arabic OCR accuracy rates, real accounts and live AI generation are not certified by these fixtures. Current metadata repair deliberately cannot fix arbitrary PDF/A/PDF/UA failures. Engine provisioning for packaged applications is separate from bundling the worker script; see the setup guide.

## Completion audit — 2026-10-27, Codex

- Creation is accessible directly from the library, including without an existing PDF. Saving a new Work/Edition returns its canonical session; stale output cannot overwrite the newly selected source.
- Existing text is editable through a textarea on the preview with explicit substitute font, alignment, size, color and direction. Embedded images can be selected, moved/resized and cropped. Organizer thumbnails paginate in batches of 36 and include imported sources; deleting all pages no longer resets the plan silently.
- Reviews add Accepted status and separate author/page filters. Arabic filtering uses search-only normalization without ambiguous taa-marbuta substitution. Summary modes include chapters, executive summary, takeaways, arguments, actions and Q&A with strict page ranges and checked quotations. Native AI verification uses an explicitly identified test double; live inference remains unverified.
- Pending Signature is backed by an actual unsigned signature widget, which certificate signing can fill. Initials/date are interactive form fields. Audit records the certificate subject/fingerprint. Offline trust checks do not establish online revocation or authoritative signing time.
- Office export preserves reconstructed paragraphs/headings/styles; HTML is now responsive semantic reflow with embedded images and escaped content, superseding the original positioned-HTML implementation. This is not exact arbitrary-layout conversion.
- Cloud export can select a staged PDF or converted DOCX/XLSX/PPTX/HTML without first replacing the saved source. Main verifies ownership, output hash, extension, signature and MIME. Real account testing stays deferred by user instruction.
- Editing/organizing/OCR retain source encryption and enforce permissions, including empty-user-password PDFs. Explicit owner-authorized decryption is a separate operation.
- Generated Arabic uses bundled DejaVu Sans and canonical ToUnicode mappings; independent PDF.js extraction asserts the exact phrase `البحث العلمي`. Source content/font maps remain untouched. See [PyMuPDF findings](PyMuPDF.md).

## Stirling-PDF (`v3.2.2`) integration — 2026-10-27, Antigravity

- **Licensing boundary**: Only Stirling-PDF's MIT-licensed `core` flavor (`./gradlew :stirling-pdf:bootJar -PstirlingFlavor=core -PdisableAdditional=true`, controllers under `app/core/src/main/java/stirling/software/SPDF/controller/api/`) is compatible with open-source integration; `app/proprietary/`, `app/saas/`, and `engine/` are governed by the proprietary Stirling PDF User License and excluded.
- **Sidecar & Loopback Adapter (`src/main/services/pdf-editor/stirling.ts`)**: Implements Stirling Desktop's exact JAR version selector (`selectNewestStirlingJar` matching `frontend/src-tauri/src/commands/backend.rs`), sidecar process launcher (`-Xmx2g -DBROWSER_OPEN=false -DSTIRLING_PDF_TAURI_MODE=true -Dserver.port=0 -Dserver.forward-headers-strategy=none -Dsecurity.enableLogin=false -Dsecurity.csrfDisabled=true`, `TAURI_PARENT_PID`, `.backend-stop-<pid>-<timestamp>` shutdown sentinel), strict loopback URL validation (`127.0.0.1` / `localhost`), Central-Directory-based streaming ZIP extraction, and `/api/v1/...` multipart execution.
- **Dual-Engine Coexistence**: Coordinate-level inspection, preview rendering, blank page creation, and coordinate-boxed Arabic RTL text overlays continue to run through `PyMuPDF` (`assets/pdf-editor/engine.py`), while supported document operations route to Stirling-PDF when `stirlingUrl` or `preferStirling` + `stirlingJar` (with JDK 25) is configured.
